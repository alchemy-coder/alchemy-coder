# Alchemy-AI 精简优化设计（v1 评审稿）

> 范围：`alchemy-ai` 模块。覆盖三层：系统提示词（Agent）→ Node 设计 → 工作流编排。
> 当前代码正处于「多智能体补充」重构中途，本设计的目标是**收敛这次重构的中间态**：删死代码、合并同构、消除字符串耦合，而不是另起炉灶。

---

## 0. 结论速览

| 维度 | 现状 | 目标 | 主要手段 |
|---|---|---|---|
| Agent 接口 | 12 个（1 个死） | 8~9 个 | 删除 `CodeWriterAgent`；`FixApplyAgent` 并入 `GenericWriterAgent`；3 个 ReviewAgent 合一 |
| 具体 Node 类 | 21 个 | 9 个 | 5 类同构 doApply 模板上收，节点变「配置」 |
| 工具权限策略 | 21 条，约 11 条引用不存在的类 | 按「角色」而非「类名」键控 | 删除 `AgentToolPolicy.fromAgentClass`，权限由 Node 显式传入 |
| 提示词常量 | 7 个证据块（3 个死）；3 套环境行 | 1 套环境行 + 参数化证据块 | 删死常量、收敛格式 |
| 状态/枚举 | `NodeEnum` 与 `WorkflowMode` 重复；`ReviewVerdict`/`TesterStatus`/`PLAN_SNAPSHOT` 死代码 | 单一事实源 | 合并枚举、接入类型化路由信号 |

**一句话结论**：这次重构的方向（角色通用 Agent + `{{scenario}}` 注入）是对的，但只完成了一半——Agent 层已经收敛，Node 层和工具权限层还没跟上，留下了大量同构样板和一处**会在运行时抛异常的漂移**。

---

## 1. 现状架构

```
ChatManager (alchemy-app)
  └─ MasterWorkflow.start(initialState)
       ├─ USER_FACE   → UserFaceNode   → UserFaceAssistant   (分流/澄清/直答)
       ├─ ROUTER      → RouterNode     → RouterAgent         (语义路由 → WorkflowMode)
       ├─ PLANNER     → PlanNode       → PlannerAgent        (需求拆解 → PLAN + 验收标准)
       ├─ PLAN_CONFIRM→ PlanConfirmNode→ ConfirmIntentAgent + HumanGate (人工确认门)
       └─ 条件边按 WorkflowMode.name() 分流到 4 个子工作流（各自是主图的一个 NodeAction）
            ├─ CODE_WORKFLOW  → CoderWorkflow    (buildQualityLoop: CODER→TESTER→DEBUGGER/REVIEWER→SUMMARIZER)
            ├─ TEST_WORKFLOW  → TesterWorkflow   (同构，节点实现不同)
            ├─ DEBUG_WORKFLOW → DebuggerWorkflow (无 REVIEWER，4 节点手写编排)
            └─ WORD_WORKFLOW  → WordWorkflow     (无 TESTER/DEBUGGER，3 节点手写编排)
```

关键数字：**168 个 Java 文件 / 14,637 行**。其中 `workflow/node/**` 21 个具体节点、`assistant/agent/**` 12 个 Agent 接口、`result/**` 12 个结果类、`tool/**` 11 个具体工具。

三层的职责分工是清晰的：
- **Agent 接口** = 提示词 + 输出 schema（`@SystemMessage` + `@UserMessage` + `@V`），纯声明。
- **Node** = 把 Agent、Result、state 读写、路由信号、进度通知、重试粘起来（`doApply`）。
- **Result** = 强类型「status + JsonNode 载荷」信封，已按角色复用（不是 1:1:1）。

问题不在分层，在于**每一层内部的重复没收敛**。

## 2. 问题清单（按严重度）

### P0 — 工具权限策略与 Agent 类名漂移（运行时会抛异常）

`ToolRegistry.getToolsForAgent(agentClass)` → `AgentToolPolicy.fromAgentClass(agentClass)` → 按 `getSimpleName()` 查表，查不到抛 `IllegalArgumentException("未知的Agent: ...")`。

而 `AgentToolPolicy` 枚举里 21 条记录用的是**重构前**的类名，约 11 条引用已不存在的类：
`CodeTestAgent` / `CodeFixAnalystAgent` / `CodeReportAgent` / `FixVerifyAgent` / `FixReportAgent` / `DocWriteAgent` / `DocReportAgent` / `TestWriteAgent` / `TestRunAgent` / `TestFixAnalystAgent` / `TestReportAgent`。

实际节点现在实例化的是 4 个**角色通用 Agent**——`GenericWriterAgent` / `ReportAgent` / `FixAnalystAgent` / `TestExecutorAgent`——**全都不在枚举里**。也就是说所有子工作流节点在 `getAssistant()` 建 Agent 实例时都会命中 `fromAgentClass` 的 throw。

深层根因：Agent 合并后「一个类 = 一套工具权限」的前提被打破了。同一个 `GenericWriterAgent`，在 CODE 场景需要 TEST/DIAGNOSTIC/SECURITY_SCAN/DEPENDENCY/NETWORK，在 WORD 场景只需要 FILE_WRITE——**权限是 (角色 × 工作流) 的属性，不是类的属性**。

### P1 — Node 层同构样板：21 个节点 ≈ 5 类模板

5 个近重复集群，每个成员 ~90~150 行，其中真正独有逻辑只有几行：

| 集群 | 成员 | 每个成员实际差异 |
|---|---|---|
| 写/改 | `CodeWriterNode` `TestWriteNode` `DocWriteNode` `FixApplyNode` | 场景串、硬约束串、commit 前缀、stepLabel（`invokeWithRetry`/`fallbackExtractFiles`/`isolateAndCommit` 完全一致，`FILE_PATH_PATTERN` 复制 4 份） |
| 测试 | `CodeTestNode` `TestRunNode` `FixVerifyNode` | 只有 `passTarget`(REVIEWER/SUMMARIZER) + 文案不同 |
| 分析 | `CodeFixAnalystNode` `FixAnalyzeNode` `TestFixAnalystNode` | 只有场景串不同（`determineNextNode`/`appendPreviousFixes` 逐字复制 3 份） |
| 审查 | `CodeReviewNode` `TestReviewNode` `DocReviewNode` | 场景串 + 是否带测试证据（`determineNextNode` 逐字复制 3 份） |
| 报告 | `CodeReportNode` `FixReportNode` `TestReportNode` `DocReportNode` | 场景串 + commitType/branchPrefix（`validateSummarizeResult` 复制 4 份） |

### P2 — 死代码与重复枚举

- `agent/code/CodeWriterAgent.java`：无任何 Node 实例化它（`CodeWriterNode` 用的是 `GenericWriterAgent`），是合并前的遗留。
- `PromptFragments.REPORT_EVIDENCE` / `REPORT_EVIDENCE_FIX` / `REPORT_EVIDENCE_DOC`：零引用（`ReportAgent` 内联了一个合并证据块）。
- `workflow/entity/ReviewVerdict.java`、`TesterStatus.java`：定义了带容错 `from()` 的类型化枚举，但**零使用**；路由仍靠裸字符串 `"APPROVED"/"REQUEST_CHANGES"/"PASS"/"FAIL"`。
- `WorkflowState.PLAN_SNAPSHOT`：零引用死 key。
- `NodeEnum.CODE_WORKFLOW/DEBUG_WORKFLOW/WORD_WORKFLOW/TEST_WORKFLOW` 与 `WorkflowMode` 四个常量**同名重复**，正确性靠「字符串名字一致」这个约定维系（`PlanConfirmNode` 返回 `mode.name()` 当路由信号）。

### P3 — 提示词格式漂移

- `JSON_OUTPUT_RULE` 在 `PlannerAgent`、`UserFaceAssistant` 里被**逐字内联重抄**；`RouterAgent`/`ConfirmIntentAgent` 又用了一个「简化变体」。
- 环境行有 **3 套格式**：`ENV_LINE`（工作目录|项目类型|日期）、`PlannerAgent`（工作目录|技术栈|模式）、`UserFaceAssistant`（只有工作目录）。
- 3 个 ReviewAgent 的 `## 核心原则`/`## 决策规则` 段近重复，各自内联 `stageResults`。

## 3. 目标设计

### 3.1 Agent 层：角色通用 + scenario 注入（收敛到位）

| Agent | 角色 | 说明 |
|---|---|---|
| `UserFaceAssistant` | 入口分流 | 保留 |
| `RouterAgent` | 语义路由 | 保留 |
| `PlannerAgent` | 规划 | 保留 |
| `ConfirmIntentAgent` | 确认意图 | 保留 |
| `GenericWriterAgent` | 写/改 | **吸收 `FixApplyAgent`**（修复场景 = scenario「最小改动修复」+ hardConstraint「只修不重构」） |
| `TestExecutorAgent` | 测试执行 | 保留 |
| `FixAnalystAgent` | 调试分析 | 保留 |
| `ReportAgent` | 收尾报告 | 保留 |
| `ReviewAgent`（新） | 质量审查 | **合并 `CodeReviewAgent`/`TestReviewAgent`/`DocReviewAgent`**，场景 + `stageResults` schema 走注入 |

结果：**12 → 9**（删 1 死类、1 并 1、3 并 1）。若担心审查场景差异过大，可先保留 3 个 ReviewAgent，则目标为 11——但 Node 层合并不受影响。

### 3.2 Node 层：模板上收，节点变配置

把 5 类 `doApply` 骨架分别上收到 5 个角色基类，具体差异收敛为一份**不可变配置**：

```
node/
  AbstractAgentNode          (保留：重试/解析/进度/上下文骨架)
  ├─ WriterNode   ← AbstractWriterNode     {scenario, hardConstraint, commitPrefix, stepLabel}
  ├─ TestNode     ← AbstractTesterNode     {passTarget, scenario, stepLabel}   (已存在，补 scenario)
  ├─ AnalystNode  ← AbstractAnalystNode    {scenario, stepLabel}
  ├─ ReviewNode   ← AbstractReviewNode     {scenario, stageResults, hasTestEvidence, stepLabel}
  ├─ ReportNode   ← AbstractReportNode     {scenario, commitType, branchPrefix, stepLabel}
  PlanNode / PlanConfirmNode / RouterNode / UserFaceNode  (保留：确有独有逻辑)
```

目标：**21 个具体节点 → 9 个**（4 个根节点 + 5 个角色节点）。工作流类变成纯装配：

```java
public class CoderWorkflow extends AbstractSubWorkflow {
  protected void buildGraph(GraphDSL g) {
    buildQualityLoop(g, new QualityLoopNodes(
      new WriterNode(WriterConfig.code()),
      new TestNode(TestConfig.code()),          // passTarget=REVIEWER
      new AnalystNode(AnalystConfig.code()),
      new ReviewNode(ReviewConfig.code()),      // hasTestEvidence=true
      new ReportNode(ReportConfig.code())));    // commitType=feat, branchPrefix=feature
  }
}
```

`DebuggerWorkflow`/`WordWorkflow` 同样用角色节点组装（DEBUG 无 Review、WORD 无 Test/Debug），把现有手写 `edge/route/toEnd` 里与 `buildQualityLoop` 重复的 `CODER→TESTER→DEBUGGER/SUMMARIZER` 片段也一并消除。

### 3.3 工具权限：从「类名查表」改为「角色显式声明」

删除 `AgentToolPolicy.fromAgentClass(Class)`。工具权限是角色的属性，由 **Node 在构造时声明**，随 `newChatAssistant` 传入：

```java
// 现状
newChatAssistant(model, GenericWriterAgent.class);        // → fromAgentClass 抛异常
// 目标
newChatAssistant(model, GenericWriterAgent.class, ToolPolicy.CODE_WRITER); // 显式角色
```

`ToolPolicy`（或直接 `Set<ToolCategory>`）与角色一一对应，`ToolRegistry.getToolsForAgent(Set<ToolCategory>)` 不再按类名。这样 Agent 合并/改名不再牵动权限表，CODE_WRITER 与 DOC_WRITE 共用 `GenericWriterAgent` 却拿到不同工具集的问题自然消失。

### 3.4 提示词收敛

- `JSON_OUTPUT_RULE` 全部引用常量，删掉 `PlannerAgent`/`UserFaceAssistant` 的内联重抄；`RouterAgent`/`ConfirmIntentAgent` 改用同一常量（它们只是 schema 更短，规则应一致）。
- 环境行统一为 `ENV_LINE` 一套；`PlannerAgent` 的 `workflowMode`、`UserFaceAssistant` 的项目类型差异改用 `@V` 参数补，不另写格式。
- 删 `REPORT_EVIDENCE*` 三个死常量；`REVIEW_EVIDENCE_DOC` 并入 `REVIEW_EVIDENCE`（测试证据段按 `hasTestEvidence` 参数化）。

### 3.5 编排层类型化

- **合并 `NodeEnum` 与 `WorkflowMode`**：子工作流节点名直接用 `WorkflowMode.name()` 注册，`NodeEnum` 只保留角色名（USER_FACE/ROUTER/PLANNER/PLAN_CONFIRM/CODER/TESTER/DEBUGGER/REVIEWER/SUMMARIZER），消除「两个枚举四个常量靠名字对齐」的脆弱约定。
- **接入 `ReviewVerdict` / `TesterStatus`**（它们已定义，只是没接）：`AbstractTesterNode.determineNextNode`、`AbstractReviewNode`、`ReportFormatter` 改用枚举而非裸字符串，路由信号从「字符串」升级为「类型化枚举 + 容错解析」。
- 顺带清理 `PLAN_SNAPSHOT` 死 key；`AbstractSubWorkflow.RESULT_KEYS` 改为按工作流声明（DEBUG/WORD 不再透传自己不产出的 REVIEW/TEST 结果）。

## 4. 分阶段实施

| 阶段 | 内容 | 风险 | 收益 |
|---|---|---|---|
| **P1 止血** | 修 `AgentToolPolicy`：先让 4 个通用 Agent 能查到权限（最小改动：补 4 条映射或临时 `fromAgentClass` 兜底） | 低 | 恢复子工作流可用 |
| **P2 删死代码** | 删 `CodeWriterAgent`、3 个死证据块、`ReviewVerdict`/`TesterStatus` 二选一（接 or 删）、`PLAN_SNAPSHOT` | 低 | 直接瘦身，零行为变化 |
| **P3 Node 收敛** | 5 个角色基类 + 配置化节点，重写 4 个工作流装配 | 中 | 21→9 节点，样板消除 |
| **P4 权限重构** | `ToolPolicy` 角色化，Node 声明权限 | 中 | 根除类名漂移，权限可组合 |
| **P5 提示词/编排收敛** | JSON_OUTPUT_RULE/ENV_LINE 统一、证据块参数化、枚举合并与类型化路由 | 低 | 契约单一事实源 |

建议 **P1 → P2 先做**（小步、可独立验证），P3/P4 是收益最大但需联调的重构，P5 是收尾。

## 5. 量化收益预估

- Agent 接口：12 → 9（-3）
- 具体节点类：21 → 9（-12，约 -1600 行同构样板）
- 工具权限：21 条含 11 条失效 → 按角色 N 条全有效
- 提示词常量：7 证据块 → 参数化后 4（删 3 死 + 并 1）
- 枚举：`NodeEnum`↔`WorkflowMode` 重复消除；`ReviewVerdict`/`TesterStatus` 由死转活

预计净删 **~2000 行**（约 14%），同时消除 P0 运行时漂移和「字符串名字对齐」这类隐性契约。

---

## 6. 明确不做什么（控制范围）

- 不重写 `AbstractAgentNode` 的 retry/parse/进度骨架——它已经够好，只在收尾时合并 3 个解析 helper 的轻微重叠。
- 不动 `GraphDSL`——构建期校验边目标是真价值，保留。
- 不动 11 个工具与 `analyzer/dependency/strategy` 策略层——它们结构清晰，不在本次「提示词/节点/编排」范围内。
- 不把 4 个工作流压成单类数据驱动——拓扑差异（有无 REVIEW/TEST）尚不构成抽象的足够理由，4 个薄类可读性更好。

## 7. 待确认

1. **3 个 ReviewAgent 是否合并为 1 个**（场景差异最大的合并，可先保留 3 个）。
2. `ReviewVerdict`/`TesterStatus` 倾向**接入**还是**删除**（接入更安全但改动面大；删除更简但保留裸字符串）。
3. 是否先做 **P1 止血**——当前子工作流在 `getAssistant()` 处会抛 `未知的Agent`，需要确认这是否已在你的待办里、还是确实是新发现。
